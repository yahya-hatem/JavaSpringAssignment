================================================================================
KEY DESIGN ACHIEVEMENTS
================================================================================

✅ POLYMORPHISM WITHOUT TYPE CHECKING
   One loop works with Books, Magazines, and DVDs asking same questions
   Each answers differently (Book 5/day, Magazine 3/day capped at 30, DVD 15/day)

✅ CAPABILITY-BASED DESIGN
   Items are renewable = implements Renewable interface
   DVDs still perfect LibraryItems but cannot be renewed
   No special DVD-handling code in the library

✅ IMMUTABLE CORE FIELDS
   catalogueId, title, membershipId, category - set once, never change
   Impossible to create invalid states

✅ CONTROLLED STATE MODIFICATION
   No public setters for balance or item count
   All changes through business methods that validate

✅ BUSINESS RULES LIVE IN MODELS
   Book knows it costs 5 EGP/day (not in a lookup table)
   Member knows it can't borrow with 100+ EGP debt
   Item knows taking it back resets everything

✅ LOAD-BEARING CODE PROTECTED
   takeBack() is final - cannot be overridden
   Prevents items staying permanently on loan

✅ MAGAZINE'S UNIQUE RULE HANDLED ELEGANTLY
   No special case in central calculator
   Magazine just caps its own fine calculation
   No if-statements checking item type

================================================================================
BUSINESS RULES ENFORCED (27 Total)
================================================================================

CATALOGUE RULES (6)
1. Catalogue IDs are unique
2. ID and title never change after creation
3. Lending only from AVAILABLE state
4. Reserved/Lost items cannot be lent
5. Return only from ON_LOAN state
6. Return always resets state, borrower, renewal count

MEMBER RULES (6)
7. Membership IDs are unique
8. ID and category never change
9. Member may hold at most 3 items
10. Member with 100+ EGP debt cannot borrow
11. Fine charged must be positive
12. Payment must be positive and not exceed balance

FINE RULES (4)
13. Days overdue must not be negative
14. Zero days overdue = no charge (no admin fee either)
15. Magazine fine never exceeds 30 EGP
16. Waiver applies to base fine only, never admin charge

RENEWAL RULES (3)
17. Only Renewable items can be renewed
18. Item can only be renewed while on loan
19. Cannot renew beyond type's limit

GENERAL RULES (2)
20. Searching for missing item/member reports it, doesn't crash
21. All operations return to menu (no early exit except explicit logout)

EXAMPLE WORKFLOW: BORROW, RETURN LATE, PAY FINE
================================================================================

HTTP Flow:

1. POST /api/library/borrow
   Request: {"catalogueId": "BOOK001", "membershipId": "M001"}
   Response: {"success": true, "loanPeriodDays": 14}

2. [14 days pass, member forgets...]

3. POST /api/library/return
   Request: {"catalogueId": "BOOK001", "daysOverdue": 5}
   Response: {
     "fineDetails": {
       "baseFine": 25.00,           // 5 days × 5 EGP
       "waiverAmount": 6.25,        // 25% student waiver
       "administrativeCharge": 10.00, // Never waived
       "totalCharged": 28.75,        // 25 - 6.25 + 10
       "newBalance": 28.75
     }
   }

4. POST /api/library/payments
   Request: {"membershipId": "M001", "amount": 28.75}
   Response: {"success": true, "newBalance": 0.0}

Internal Logic Flow:

Step 1: Service finds BOOK001 (status = ON_LOAN)
Step 2: Service finds member M001 and identifies him from book's borrower field
Step 3: Book answers: "5 days overdue costs me 5 × 5.00 = 25.00 EGP"
Step 4: Member answers: "I'm STUDENT, so my waiver is 25% × 25.00 = 6.25 EGP"
Step 5: Service adds non-waivable admin charge: 10.00 EGP
Step 6: Service charges: 25.00 - 6.25 + 10.00 = 28.75 EGP
Step 7: Member's chargeFine() accepts (positive amount)
Step 8: Member's recordReturn() decrements item count
Step 9: Item's takeBack() resets state, borrower, renewal count
Step 10: Both saved to database (transactional)

WHAT MAKES THIS DESIGN SPECIAL
================================================================================

Unlike typical library systems that have:
   - A "FineCalculator" class with switch statements
   - A "ValidationService" checking item types
   - A lookup table mapping categories to waivers
   - Special cases and if-statements scattered throughout

This system has:
   ✓ Each item type knows its own rules (no switch statements)
   ✓ Each member type knows its own waiver (no lookup tables)
   ✓ Polymorphism allows same loop to handle different items
   ✓ Interfaces express capabilities not categories
   ✓ Models enforce rules, not just data containers
   ✓ Magazine's unique "capped fine" rule just works
   ✓ Adding new item type = just one new class
   ✓ Code that loops over items never changes when types change

This is Object-Oriented Programming done right: objects know how to 
answer questions about themselves, and the system asks, rather than 
the system deciding on behalf of objects.
